# ADR 0014 — Google Play real-time notifications (webhook)

**Status:** Accepted · **Date:** 2026-11-05

## Context
After ADR 0013 the backend only learns about a subscription when the app sends its receipt again. Renewals, cancellations, grace periods and, above all, refunds and revocations before the stored end date stayed invisible. Google publishes these changes as real-time developer notifications (RTDN) through Cloud Pub/Sub ([reference](https://developer.android.com/google/play/billing/rtdn-reference), [setup](https://developer.android.com/google/play/billing/getting-ready#configure-rtdn)). The reference says a notification only tells that the state changed, that the full state must be read from the Play Developer API, and that `messageId` should be checked to avoid duplicate work.

## Decision
- **`POST /v1/webhooks/google`, not behind an API key** (Pub/Sub cannot send one). The proof is the OpenID Connect token that a push subscription with authentication sends in `Authorization: Bearer` ([docs](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions)). It must be signed by Google, issued by `https://accounts.google.com`, not expired, for our audience (`KUOTAKIT_GOOGLE_PUBSUB_AUDIENCE`), and have the verified email of our push service account (`KUOTAKIT_GOOGLE_PUBSUB_SERVICE_ACCOUNT_EMAIL`). It uses Google's `GoogleIdTokenVerifier` behind the domain port `PushTokenVerifier`. Without the configuration the endpoint answers 401 to everything.
- **A notification may only take access away without asking Google.** A voided purchase (`REFUNDED`) and `SUBSCRIPTION_REVOKED` (`REVOKED`) are applied straight from the verified message, because that can only reduce access. Every other change re-reads `subscriptionsv2.get` and maps it with the same `PlaySubscriptionMapper` as the receipts, so renewals, holds, pauses, recoveries and expiries share one tested rule. Price-only notifications (types 8, 19, 22) are ignored; an unknown future type is read again, which is cheap and safe.
- **`REFUNDED` and `REVOKED` are final, and the storage enforces it.** `PurchaseRepository.save` ignores any write to a purchase in a final status (the check is in the same SQL statement as the write; the first reason is kept). That covers three things at once: a later notification, the receipt endpoint (the app sending the receipt again while Google may still describe the subscription as active), and a slow update that read the purchase before the refund (a renewal being read from Google while the refund lands cannot undo it). A final purchase also costs no call to Google, and a receipt for it is not acknowledged again. Another user still cannot take its token (`409`). The review of this task found that the first version enforced "final" only inside the notification service.
- **The webhook never creates a purchase.** It cannot know the user. A notification for a token nobody submitted (for example `SUBSCRIPTION_PURCHASED` arriving before the receipt) is acknowledged; the receipt endpoint reads fresh state anyway.
- **Answers.** 204 for everything that was handled or can never succeed (another app, a test message, a one-time product, an unknown purchase, a purchase Google no longer describes, and **a body that cannot be read or is too large**): a non-2xx would make Pub/Sub retry it for days. The check of the proof comes first, so an unauthenticated garbage body is a 401, never a 204; once the proof is valid the push came from our own subscription and an unreadable body will be unreadable on every retry, so it is dropped with a warning in the log. There is no 400. 401 when the proof fails. 502 when Google (or its signing keys) cannot be reached, so Pub/Sub retries.
- **Duplicates.** `store_events(store, message_id, received_at)` (migration V3). The message is recorded **after** it was handled, so a failure is retried and never lost; handling is idempotent (it re-reads Google), so two concurrent copies are harmless and this only saves API quota. Rows older than 14 days (twice Pub/Sub's retention) are deleted on each insert.
- **Parsing.** The Google payload is read as a JSON tree in `backend.google`, not with new `@Serializable` models: those shapes belong to Google, and models live only in `contracts/`. The body is limited to 16 KiB (the same limit as a receipt).
- **Garbage never causes a retry.** A bearer token that cannot be parsed is `401`; only a failure to fetch Google's keys is `502`. (A first version treated every `IOException` as "keys unreachable", which would have made Pub/Sub retry a forged push for a week; a test with garbage while the keys are down caught it.)

## Assumptions we could not verify
- A `voidedPurchaseNotification` for a subscription (`productType` 1) means the purchase lost its entitlement. The reference describes it as a voided purchase, but nothing in it or in our tests establishes, for example, that a partial refund of one recurring order never arrives this way. If it did, a user would be denied wrongly (fails closed) and, because the status is final, only manual repair would undo it.
- Price-only notification types (8, 19, 22) do not change who has access: our reading of the reference.

## Known limits
- **A refund or revocation that arrives before the first receipt was lost in this version (fixed by ADR 0016, which keeps it for 60 days).** If the notification for a token nobody has submitted yet is acknowledged (204) and the receipt arrives later, the receipt reads Google's state, which may still look active. Likely rare (a purchase refunded before the app ever sent its receipt); a table of pending revocations would close it and is not part of this task.
- **Two non-final updates for one token** (for example a hold and a recovery read from Google at nearly the same time) are last-write-wins: both are states Google reported, and the later notification or receipt corrects it. Only the final statuses are protected.
- The real verifier is tested on its own with signed tokens; the route tests use a fake verifier, and the wiring in `Main.kt` from the configuration is not covered by a test.
- Logs are not tested for purchase tokens; the code never puts one in a log line, and the responses are fixed texts.
- **Never run against the real Pub/Sub or the real Play.** Tested with tokens signed by a throw-away RSA key and the client library's mock transport. The real check needs a public HTTPS URL and an app on an internal test track (end of Phase 1).
- Whether `subscriptionsv2` reports a refund immediately, and whether `expiryTime` moves during a grace period, is unconfirmed; the refund path does not depend on the first.
- A notification for a purchase whose plan changed (`SUBSCRIPTION_ITEMS_CHANGED`) can be rejected by the mapper because the stored product is no longer in the subscription; the stored end date still limits access. Plan changes arrive with `linkedPurchaseToken` (next task).
- One-time products arrived later (ADR 0015); rate limiting is not part of this task.
- Pub/Sub's retry policy (backoff, dead-letter topic) is configured in the subscription, not here.

## Alternatives considered
- **Pull subscription** (the backend polls Pub/Sub): needs credentials and a long-running consumer; the official guidance suggests push as the simpler start.
- **Re-reading Google for refunds too:** fewer rules to trust, but a refund would depend on how fast and in which form `subscriptionsv2` shows it, which the docs do not say; a verified message that can only remove access is the safer shortcut.
- **Recording the message before handling it:** simpler, but a crash or a Google outage between the two would lose the update for good.
- **Hand-written verification of the JWT:** more code to get wrong; the Google library already implements the signature, expiry, issuer and audience checks.

## Amendment (2026-11-13): verified with the real Google
Run with the real Pub/Sub and Play Console (topic, push subscription with authentication, endpoint behind a temporary tunnel; plan `docs/plans/2026-11-rtdn-real-google.md`). Observed: the OIDC token of the push service account was accepted; the test message was handled as `IGNORED`; a purchase notification can arrive **before** the receipt of the app (`UNKNOWN_PURCHASE`, answered so that nothing is lost; the receipt of the app saves the purchase); a cancel made in Play Store reached the backend in about 30 seconds as `UPDATED` (`auto_renewing=false`); a refund by the API in about a second as `UPDATED` (`refunded`), followed by `ALREADY_FINAL` for later messages of the same purchase. Not exercised: a duplicate push, retries after an outage, a stable address. Public API: none.
