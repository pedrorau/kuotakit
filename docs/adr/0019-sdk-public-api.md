# ADR 0019 — The public API of the SDK (subphase 1a)

**Status:** Accepted · **Date:** 2026-11-12

## Context
ADR 0002 splits the SDK into a Kotlin Multiplatform core and thin adapters, one per store. ADR 0003 says the client never grants access, ADR 0013 that the backend acknowledges purchases, and ADR 0017 that every Google purchase must carry the account id. The public API of the SDK is a contract (rule 4 of AGENTS.md), so its shape is decided here. Plan: `docs/plans/2026-11-sdk-android-1a.md`.

## Decision
- **Two modules:** `sdk/core` (Kotlin Multiplatform: jvm, android, iosArm64, iosSimulatorArm64; `explicitApi()`; public API dump in `sdk/core/api/`) and `sdk/android` (the Play Billing adapter). The API models are the ones of `contracts/`, never copies.
- **The core** offers `KuotaKit.configure(KuotaKitConfig(baseUrl, apiKey, billing, storage))`, `KuotaKit.shared`, `appUserId`, `getOfferings()`, `getCustomerInfo()`, `purchase(pkg)` and `customerInfo`, a `StateFlow` of the last customer info the backend gave. It also defines the two interfaces a platform implements: `BillingAdapter` and `KeyValueStore`.
- **Failures are exceptions of one sealed class**, `KuotaKitException`, one subclass per row of the table "Errors" of `docs/api-spec.md` plus `Network`, `Unexpected`, `NotConfigured` and `InvalidConfiguration`. The code in the error body decides, not only the status; a body that is not the error body of the contract, or a code the SDK does not know, is `Unexpected`. A cancelled purchase and a pending payment are outcomes (`PurchaseOutcome`), not failures.
- **The SDK never computes access.** `purchase` returns exactly the customer info the backend answered, and a failure leaves `customerInfo` as it was.
- **The adapter never acknowledges:** the backend does, after it checked the purchase (ADR 0013). The Android interface to Play Billing has no acknowledge call.
- **The adapter attaches `playObfuscatedAccountId(appUserId)`** to the purchase when it starts it (ADR 0017); the core computes it and passes it in the `PurchaseRequest`.
- **A secret API key is refused:** `configure` throws `InvalidConfiguration` for a key that starts with `sk_` (rule 3: no secrets in an app) and for one that does not start with `pk_`.
- **The anonymous app user id** is `$anon_` and a random UUID in hex (38 characters, 122 random bits), made once and kept in a `KeyValueStore` (on Android, the app's private preferences). One that was stored but is not valid is replaced.
- **HTTP:** Ktor client (OkHttp on the JVM and Android, Darwin on iOS), a bearer API key, timeouts, no automatic retries.
- **Play Billing Library 9.1.0** (release notes of 2026-06-18), with its Kotlin extensions. A product is looked up as a subscription and, if Google does not know it as one, as a one-time product, because the app only knows its id and the backend decides the kind (ADR 0015). The offer is the base plan, else the first one the user is eligible for.

## Consequences
- A change of the public API shows in the dump and in review.
- The iOS adapter (Phase 2) implements the same `BillingAdapter` and reuses the core.
- Known limit of 1a: if the user buys and the backend cannot be reached when the receipt is sent, `purchase` fails and the purchase stays unacknowledged at Google (refunded after three days). It fails closed, but the user can lose the purchase until subphase 1b adds `restore` and the retry.
- A purchase update that Google sends when no `purchase` call is waiting for it (the call was cancelled while the Play screen was open, a pending payment that completes later, the process was killed) is not sent to the backend in 1a; `restore` in 1b recovers it. A user who already owns an unconfirmed purchase gets `InvalidRequest` when buying it again, for the same reason.
- `ITEM_ALREADY_OWNED` is Google Play's own answer: a subscription or a non-consumable product cannot be bought twice, which is right. Subphase 1b turns it into a recovery of the purchase (look up what the user owns and send the receipt) instead of an error.
- The core never holds the `Activity`: the lambda that gives it lives as long as the SDK, so an app must not capture the activity in it (keep a weak reference).
- Not run on a real device or against the real Google: the code of `BillingClientPlayClient` (the part that talks to `BillingClient`) has no unit test, only the adapter and the failure mapping around it do; it is checked on a device in the task of the example app.

## Alternatives considered
- **`HttpURLConnection` or OkHttp directly:** not multiplatform; the core would need one client per platform.
- **A `Result` type for everything:** heavier for app code; exceptions suit suspend functions and bridge easily.
- **Acknowledging in the app (client-only):** would grant before the server agrees (ADR 0003).
- **The plain app user id as the account id:** rejected in ADR 0017.

## Amendment (2026-11-12, subphase 1b-i): restore and recovery of purchases
Plan: `docs/plans/2026-11-sdk-android-1b-i.md`. Read against the Play Billing documentation ("Detect and process purchases", `ITEM_ALREADY_OWNED`, `Purchase.getAccountIdentifiers`).
- **Google Play is the queue of purchases to send.** The SDK stores nothing: a purchase that could not be sent is found again in the next sync, because Google keeps it until it is confirmed or refunded. `restore()` queries what the user owns, sends the ones that are `PURCHASED` and carry the account id of this app user, and returns what the backend says afterwards (`RestoreOutcome`: the customer info, how many purchases were accepted, how many the backend refused, and how many were found in the store but not sent because they carry no account id or another one). A purchase refused with `402`, `409` or `400` counts as refused and does not stop the others; a failure to reach the backend (`Network`, `StoreUnavailable`, `RateLimited`, `Unauthorized`, `Unexpected`) stops the restore with its exception.
- **What a sync does with a purchase is one explicit decision** (`OwnedAction`): `Send` (completed, this account id), `Waiting` (pending: sent when the store says it is completed), `NotOurs` (no account id, or another one: the backend would refuse it, ADR 0017) and `Ignore` (any other state). A failed query of owned purchases is an exception, never an empty list.
- **`BillingAdapter` gains `ownedPurchases()` and `purchaseUpdates`:** the updates are purchases that arrive while no `purchase` call is waiting (a pending payment approved later). The core listens from `configure`, runs a sync at start and one for every update, one at a time. A failure in the background changes nothing visible; there are no timers: the triggers are `configure`, an update, `ITEM_ALREADY_OWNED` and `restore()`, which the app calls when it comes to the foreground (Google recommends syncing when the connection is made).
- **`ITEM_ALREADY_OWNED` becomes a recovery:** `purchase` runs a restore and returns `PurchaseOutcome.AlreadyOwned(customerInfo)` if it sent something; if no owned purchase carries this app user's account id it throws `InvalidRequest` saying the purchase was made under another app user id or outside the app.
- **The Android adapter has two layers:** `PlayBilling` decides (order of lookups, subscription before one-time product, a failed query is an error, only the product asked for in the state `PURCHASED`, the single waiting purchase call, forwarding of the other updates) and is unit tested with a fake `PlayClient`; `BillingClientPlayClient` only translates to and from Google's classes and is checked on a device.
- **The backend limits the receipts of one app user** (10 a minute by default, ADR 0016), so a purchase the backend already answered, accepted or refused, is not sent again in the same run of the app; the customer info is read every time, which is where renewals and refunds show. Sending a receipt again is safe for the backend (it reads the purchase again and saves it; it does not acknowledge twice), but it costs budget. If the limit is reached the restore stops with `RateLimited` (the app sees it; in the background it is kept for the next trigger).
- **Only the update that answers the waiting purchase call is taken by it:** one for another product (a pending purchase approved meanwhile) is forwarded to the sync instead. `purchaseUpdates` is hot only while the SDK listens, from `configure`; an update that Google reports with nobody listening, or beyond the buffer, is not delivered, which is recoverable: every sync asks the store for everything the user owns.
- **Whatever goes wrong in the background** (a failure of the store, of the network, or a bug) is kept for the next trigger and never ends the app; calling `configure` again stops the sync of the previous instance (call it once). The old `BillingClient` of an earlier `configure` is not closed: one more reason to call it once.
- **`AlreadyOwned` is only returned if the product asked for was among the purchases the backend accepted** in this run of the app; if the backend refused what the store says is owned, `PurchaseInvalid`; if nothing of this app user was found, `InvalidRequest`.
- **Limits that remain** (identity is out of v0, ADR 0005): a purchase made outside the app (a promo code), on another device with another app user id, or before a reinstall carries another account id and cannot be recovered; the SDK says so instead of staying silent. The limits of 1a about a lost receipt and a second purchase of the same product are closed by this amendment.
- **A `purchase` call waits for the answer of the Play screen** with no time limit: if the process stays alive but Google never answers, the call and the lock that serializes purchases stay waiting. Google reports a dismissed screen as a cancel, so it is not expected; it is recorded here, not handled.
- **The public data classes** (`OwnedPurchase`, `RestoreOutcome`, `PurchaseRequest`, the results) expose `copy` and `componentN`, and `OwnedState.OTHER` is a public enum case: both are reconsidered in subphase 1b-ii, before the public API is closed.
