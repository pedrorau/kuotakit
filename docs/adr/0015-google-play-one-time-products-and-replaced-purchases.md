# ADR 0015 — Google Play one-time products and replaced purchases

**Status:** Accepted · **Date:** 2026-11-05

## Context
ADR 0013 validates subscriptions and ADR 0014 receives their notifications. v0 also sells non-consumable one-time purchases (ADR 0005) and a subscription can replace another (an upgrade, a new sign-up), in which case Google asks the backend to stop honouring the old token. Official sources: [one-time purchase lifecycle](https://developer.android.com/google/play/billing/lifecycle/one-time), [`purchases.productsv2`](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.productsv2) and [subscription lifecycle](https://developer.android.com/google/play/billing/subscriptions).

## Decision
- **The server decides what kind of product it is.** `entitlements.yaml` gets an optional `one_time_products` (per store); every product listed must grant an entitlement, like the offered ones. Any product not listed is read as a subscription. The receipt of `contracts/` does not change, so there is no change to the public API and the app cannot ask for the wrong endpoint.
- **One-time receipts** use `purchases.productsv2.getproductpurchasev2` and, if needed, `purchases.products.acknowledge`, in the same order as subscriptions (read, check, acknowledge, save) and with the same ownership rules (`obfuscatedExternalAccountId`). `PURCHASED` is `ACTIVE` with no end date (`NON_CONSUMABLE`). `PENDING` and unknown states are refused with 402; `CANCELLED` is refused for a purchase we never held and is `REVOKED` for one we hold. `refundableQuantity` of 0 (or less) means everything was refunded: `REFUNDED`. **A missing `refundableQuantity` grants nothing** (402): it is the only sign of a refund on a completed purchase, a one-time purchase never expires, and JSON often leaves out a zero, so reading "missing" as "nothing refunded" would give a refunded lifetime unlock for free. If the real Google omits it for normal purchases this will show on the first real test and must be revisited. Consumables stay out of v0, so `consume` is never called.
- **Notifications.** `oneTimeProductNotification` (bought, cancelled, any type) and a voided one-time purchase with a partial refund re-read the purchase; a full voided one-time purchase is a refund like a voided subscription (ADR 0014). The re-read uses the API that matches the *stored* kind, so a notification cannot make a subscription be read as a one-time purchase (tested both ways). When Google stops describing a stored **one-time** purchase (an error for the token, an unknown or pending state, the product missing, no refundable quantity), it becomes `EXPIRED` as of now, which is not final: with no end date to bound it, keeping it active would keep it forever, and the next good read restores it. A subscription in the same situation is left alone because its stored end date bounds it. For these the Play Console option "all notifications for subscriptions and one-time products" is needed.
- **Replaced purchases.** If a subscription carries `linkedPurchaseToken`, the old stored purchase becomes `EXPIRED` as of now, **after** the new one was saved, so a refused or failed new purchase never leaves the user with neither. It applies whoever owned the old token, because Google says the entitlement moved; it is not final, and a refunded or revoked old purchase keeps its reason. Google's lifecycle table says the old token then reads as expired; that is not verified here, and if Google still reported it active a later read of the old token would restore it until its own end date. Only a subscription can be replaced, and a link to the purchase itself is ignored. It runs both on a receipt and on a notification for the new token.
- **Pitest.** The mutation job now runs every test of the `domain` package against any mutated class. By default the plugin runs only tests whose name matches the mutated classes, which ignored tests named after a feature (`OneTimeReceiptServiceTest`) and made a partial run score 54 % where the same tests score 73 %. The full-package score (80 %) and the 70 % threshold are unchanged.

## Known limits
- **Deferred replacements are not supported.** When a replacement is deferred, the new token has two line items and the new product has no `expiryTime`; the mapper refuses a granting state without an end date (402), and a receipt that names the old product is read as that old product until it ends. Immediate replacements are covered.
- Only the line item named by the receipt is read; a one-time purchase with several products, and multi-quantity purchases beyond `refundableQuantity`, are not modelled.
- A partial refund of a multi-quantity one-time purchase leaves it `ACTIVE`: we do not track units.
- `testPurchaseContext` is ignored: a purchase with a test card counts as real.
- Whether a voided-purchase notification for a one-time product always means the user lost it is assumed, as for subscriptions (ADR 0014).
- Rate limiting and a table of refunds that arrive before the first receipt are the next task (2d).
- `one_time_products.app_store` is accepted and ignored until the App Store adapter exists (Phase 2).
- Pitest scores quoted here were measured locally with the new configuration (partial run 73 %, whole package 80 %); the threshold applies to the whole package.
- Not run against the real Google: tested with the client library's mock transport.

## Alternatives considered
- **A `product_type` field in the receipt:** the SDK knows it, but it changes `contracts/` and its public API dump, and the backend would trust the app for which endpoint to call.
- **Try subscriptions, then one-time purchases:** needs no configuration but doubles the calls and relies on guessing which error Google returns for the wrong kind, which the docs do not say.
- **Mark the old token `REVOKED`:** simpler, but final, and Google already shows it as expired; an `EXPIRED` old purchase agrees with whatever Google says later.
