# ADR 0017 — A Google Play purchase must carry the account id of its buyer

**Status:** Accepted · **Date:** 2026-11-06

## Context
ADR 0013 accepted a purchase that carried no account id: whoever sent a valid token first got it. The public API key is in every copy of the app, so anyone who got hold of another buyer's purchase token could claim it before the buyer did. Google's guidance ([security](https://developer.android.com/google/play/billing/security)) is to bind the purchase to the user when the billing flow starts, with `setObfuscatedAccountId`, and to check on the backend that the purchase "matches the expected user account in your system".

Facts from [`BillingFlowParams.Builder`](https://developer.android.com/reference/com/android/billingclient/api/BillingFlowParams.Builder#setObfuscatedAccountId(java.lang.String)): the identifier "is limited to 64 characters"; it must not hold personal data in clear text, which "results in purchases being blocked"; Google "recommends that you use either encryption or a one-way hash". An app user id can have up to 128 characters and, in KuotaKit, **is a secret** (ADR 0009): whoever knows it can read that user's data.

## Decision
- **The value is `playObfuscatedAccountId(appUserId)`, in `contracts/`:** the SHA-256 of the app user id as 64 lowercase hexadecimal characters. It fits the limit exactly, it is the one-way hash Google recommends, and it does not send the secret to Google. SDKs and backends use the same function, so they cannot disagree.
- **A purchase with no account id is refused** (`402 purchase_invalid`, nothing stored, nothing acknowledged). **A purchase with another account id is `409 token_already_linked`**, which includes the app user id in plain text and the hash in upper case. Only an exact match is accepted. It applies to subscriptions and one-time purchases; notifications do not claim purchases, so they are not affected.
- **No setting turns it off.** The safe behaviour is the default and the only one. An app with its own client must call `setObfuscatedAccountId` with that hash when it starts the purchase (docs/google-play-setup.md).
- **"Whoever stored the token first keeps it" stays** as a second line of defence: with the account id enforced it can only matter for data that predates it.
- **SHA-256 is written in plain Kotlin** in `contracts/`: Kotlin Multiplatform has none in its standard library, and `contracts/` may use only Kotlin and kotlinx (a Konsist rule). It is checked against the official FIPS 180-4 vectors, on every platform that runs the tests, and on the JVM against `MessageDigest` for every size from 0 to 300 bytes (the block boundaries where padding changes), long inputs and random ids; a wrong round constant breaks them (tried while the code was written). The only public symbol added is `playObfuscatedAccountId`.

## Known limits
- **The hash of a guessable id can be guessed.** The SDK generates random ids, so it is not a concern for them; an app that chooses its own short ids and sends them to Google through this field should know that the hash is not a secret from someone who can try ids. The id remains the user's secret (ADR 0009).
- **Reinstalling the app creates a new anonymous id** (ADR 0005 leaves identity out of v0), so a purchase made under the old id cannot be claimed by the new one. This was already true when the token was stored for the old id; now it also holds for tokens not yet stored.
- **Purchases that do not start in the app's billing flow have no account id and are refused.** A promo code redeemed in the Play Store, a resubscription from Play's subscription centre, or a purchase on another device that runs an old build of the app carries none. If the app finds such a purchase after a restore and submits it, the answer is `402` and the purchase is not acknowledged; Google's documentation says that a purchase not acknowledged within three days is refunded and revoked ([one-time lifecycle](https://developer.android.com/google/play/billing/lifecycle/one-time)). A paying customer can lose such a purchase. This is the price of the rule and it is accepted for now; ways to soften it are a decision for later (for example an SDK that tells the user before the three days are up, or a policy that accepts a purchase without account id under stricter conditions).
- **Upgrades and downgrades must carry the account id too.** Google's reference lists `setObfuscatedAccountId` as optional "to replace an old subscription", so the replacement flow can carry it; the SDK must set it there as well. A replacement without it is refused like any other and the plan the user already has is left alone (tested). Whether Google carries the id over by itself on a replacement is not known and is not relied on.
- **Google recommends revoking and refunding a purchase that fails these checks** (`purchases.subscriptionsv2:revoke`, `orders.refund`) instead of letting it auto-refund. This backend does not do it: it refuses the purchase and does not acknowledge it, so, according to the documentation quoted above, Google refunds it after three days (not tested against the real Google). An active refund is a destructive action on real money and needs its own decision.
- Purchases made before an app sent the account id (there are none in a KuotaKit backend yet) would have to be re-bought or fixed by hand.
- Nothing is trimmed or normalised before comparing: the value must be exactly the 64 characters the function gives (tested). If the real Google changed what was sent (case, spaces, length) purchases would be refused with `409` until the SDK or this check is adapted; the documentation does not say it does.
- Not run against the real Google: the field's behaviour on real purchases (that it comes back in `subscriptionsv2` and `productsv2` exactly as sent) is taken from the documentation and the client library, not from a real order.

## Alternatives considered
- **The app user id in clear text:** simplest, but ids over 64 characters would not fit, Google may block purchases that look like personal data, and the secret id would leave our control.
- **An HMAC with a secret from the backend:** the app would need the secret, which must never be in the app (rule 3); or a round trip to the backend before every purchase.
- **A setting to allow purchases without it:** a switch that reopens the hole by default for anyone who forgets it.
