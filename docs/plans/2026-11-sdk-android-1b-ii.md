# Plan: the SDK for Android, subphase 1b-ii (plan changes, offline cache, end-to-end test, closed API)

- **Origin:** context (subphase 1b was split in two by the maintainer on 2026-11-12; this is the second half). Reviewed against the official Play Billing documentation before writing (sources below).
- **Approved by the maintainer on:** 2026-11-12 (with the offline policy A and `DEFERRED` supported, after the backend task that came first, #18)
- **Branch / PR:** `feat/sdk-android-1b-ii` / not started

## Goal
The Android SDK is complete for v0: a subscriber can change plan from the app (carrying the account id), the app can show what the user had when there is no network without the SDK ever granting access, the SDK is proven against the real reference backend and its fake Google (no device needed), and the public API is reviewed and frozen for the first release. When it is merged, Phase 1 only lacks the example app, the check against the real Google and the audit of implicit state machines.

## What the official documentation says (read on 2026-11-12) and what it changes
Sources: [Subscriptions: upgrade, downgrade or change](https://developer.android.com/google/play/billing/subscriptions), [migration to Play Billing Library 8](https://developer.android.com/google/play/billing/migrate-gpblv8).
- **A plan change is a new purchase flow that names the old purchase.** For a change between two products the app specifies the replacement "at runtime as part of the purchase flow parameters": `BillingFlowParams.SubscriptionUpdateParams` with `setOldPurchaseToken(...)` and `setSubscriptionReplacementMode(...)`. The newer, "preferred" way is `SubscriptionProductReplacementParams` (`setOldProductId`, `setReplacementMode`) on each `ProductDetailsParams`, designed for subscriptions with add-ons; for one product replacing one product, `SubscriptionUpdateParams` is enough and is not deprecated. `setObfuscatedAccountId` is set on the same `BillingFlowParams`, so the replacement carries the account id exactly like a first purchase (ADR 0017).
- **Replacement modes** (`WITH_TIME_PRORATION`, `CHARGE_PRORATED_PRICE`, `CHARGE_FULL_PRICE`, `WITHOUT_PRORATION`, `DEFERRED`, `KEEP_EXISTING`). Restrictions: switching **to a prepaid plan** allows only `CHARGE_FULL_PRICE`; switching plans **within the same subscription to an auto-renewing plan** allows only `CHARGE_FULL_PRICE` and `WITHOUT_PRORATION`; `KEEP_EXISTING` is for add-ons and is not supported in `SubscriptionUpdateParams`. Google fails the purchase with an error otherwise.
- **`DEFERRED` issues the new purchase immediately and the old plan keeps giving access until it ends.** Google recommends it for downgrades. The backend refuses such a purchase today (scenario L2-37) and does not acknowledge it, so Google would cancel the change after three days: that is why the maintainer decided on 2026-11-12 that it must be supported, in its own task before this one (`docs/plans/2026-11-backend-deferred-plan-changes.md`). The SDK offers it here, and the end-to-end test includes a deferred change.
- **Which purchase is replaced is found in the store:** the old purchase token comes from the purchases the user owns, which the SDK already queries (1b-i). The SDK looks up the owned subscription of the product the app names, attributed to this app user (account id) and in the state `PURCHASED`; if there is none the call fails with a clear error and nothing is launched.
- **What the backend does with it already exists:** the new purchase names the old token in `linkedPurchaseToken` and the backend expires the old purchase once the new one is saved (ADR 0015, scenarios L2-19 and L2-37). Nothing changes in the backend.

## Scope
- **Plan changes:** `purchase(pkg, change = PlanChange(replacing = <package or product id>, mode = ReplacementMode.…))` in the core, with `ReplacementMode` = `CHARGE_PRORATED_PRICE`, `WITH_TIME_PRORATION`, `CHARGE_FULL_PRICE`, `WITHOUT_PRORATION` and `DEFERRED`. `PurchaseRequest` carries the replacement; the Android adapter finds the old purchase token among the owned subscriptions of this app user and builds `SubscriptionUpdateParams` in the thin real client. The account id is attached as in any purchase. Outcomes are the same (`Success`, `Cancelled`, `Pending`, `AlreadyOwned`).
- **Offline cache of the customer info (see the decision below):** the last customer info the backend gave is kept in the `KeyValueStore` (as JSON, with the moment it was received) and offered as `lastKnownCustomerInfo`, never as an answer of the backend and never granting anything the SDK computed; it is replaced by every answer and dropped when the app user id changes. Reading it needs no network.
- **An end-to-end test with no device:** a new JVM module `sdk/e2e` runs the core of the SDK against the reference backend and the fake Google of the conformance suite, started with Docker Compose (a small override publishes the ports). A fake `BillingAdapter` plays Google Play: it scripts the fake Google with what Play would report (taking the account id from the `PurchaseRequest`), so it proves that the account id the SDK computes is the one the real backend accepts, and that every error of the real backend reaches the app as the right exception. Scenarios: buy a subscription; buy a one-time product; a pending then approved payment; a refund; a purchase of another app user; a plan change (immediate and deferred); restore after a lost receipt; the backend down; a wrong key; the rate limit. A CI job `sdk-e2e` (in the `needs` of `ci`).
- **Closing the public API (reviewed before the first release):** value types become plain classes with `equals`, `hashCode` and `toString` instead of data classes (no `copy` or `componentN` in the contract); `OwnedState.OTHER` becomes `UNKNOWN`, like every other enum of the project (AGENTS.md); a list of what is public and why, in the ADR; the dump regenerated.
- **Docs:** ADR 0019 amended (or a new ADR if it grows), `docs/sdk-android.md` complete (plan changes, offline, what is public), AGENTS.md, the plan and the session log.

## Out of scope
- `KEEP_EXISTING`, subscriptions with add-ons, prepaid plans and their top-ups, installments, offers and promotional pricing, in-app messages.
- A real device and the real Google (the example app task), the iOS adapter (Phase 2), bridges (Phase 3), publishing (Phase 4).
- Purchases made outside the app or under another app user id (identity is out of v0, ADR 0005).

## Decisions
1. **Offline policy: still to decide, after looking at other SDKs (2026-11-12).**
   - **RevenueCat** keeps the user id and the `CustomerInfo` on the device and returns the cached one offline ([caching](https://www.revenuecat.com/docs/test-and-launch/debugging/caching)): refreshed after 5 minutes in the foreground, 25 hours in the background, or after a purchase or restore; and an entitlement that was active when the device went offline "stays active for up to three days", then stops being shown as active until the user reconnects. A separate "offline entitlements" feature computes access from the receipts on the device when *their server* is down.
   - **Adapty** returns the cached profile when the server cannot be reached and refreshes about once a minute ([subscription status](https://adapty.io/docs/subscription-status)); an opt-in "local access levels" grants access from the device only when *their servers* are down ([local access levels](https://adapty.io/docs/fr/local-access-levels.md)). I did not find a documented cache duration.
   - So the common practice is that the SDK itself keeps the cached answer working offline for a limited grace period, which is more lenient than option A. What I did not check: whether they sign or verify the cached data; a user who edits the stored file can extend the grace, which is why signed responses would be needed for a serious offline mode.
   - **Options for KuotaKit:** **A** (strict): `lastKnownCustomerInfo` with the moment it was received, no interpretation by the SDK; the app decides. **C** (like RevenueCat): the same plus a grace period, set by the app (default 3 days), within which the SDK reports the cached entitlements it was given as active offline, and never beyond `expires_at`; it only repeats what the backend said, for a limited time, but it is the SDK deciding for the app. **C needs signed answers from the backend to be trustworthy** (a later task); without them a rooted device can tamper with the cache.
   - **Recommended: A now**, documenting the trade-off, and C together with signed customer info later. A is the only option that keeps rule 1 (entitlements come only from the backend) untouched.
2. **`DEFERRED` is supported** (maintainer, 2026-11-12), by a backend task that comes first.
3. **The end-to-end test as its own module and CI job**: explained to the maintainer in the conversation: it needs Docker (backend, Postgres and the fake Google in containers, about two minutes), so it cannot be part of `./gradlew build` or of the `jvm` and `ios` jobs that everybody runs; a separate Gradle module (`sdk/e2e`) is only run when asked, and a separate CI job (`sdk-e2e`) runs it like the existing `conformance` job does.

## Acceptance criteria
- [x] A plan change names the old purchase found among the owned purchases of this app user, carries the account id and one of the four immediate modes — checked by: tests with the fake `PlayClient` (the old token is passed, the account id is passed, a product the user does not own fails with `InvalidRequest` and nothing is launched, a pending or another user's purchase is not replaced) and with the core (the request carries the replacement).
- [x] The core exposes the five replacement modes and no other (`KEEP_EXISTING` is for add-ons) — checked by: a test per mode and the ABI dump.
- [x] The cache is read with no network, replaced by every backend answer, dropped when the app user id changes, and never the source of `customerInfo` nor of a success — checked by: tests with a fake store and a MockEngine that fails; a negative check that makes the cache win over the backend.
- [x] A corrupt or unknown cached value is ignored, never an error — checked by: a test with garbage in the store.
- [x] The SDK works against the real reference backend: a purchase with the account id of the SDK is accepted and gives `premium`; every error row reaches the app as its exception; restore recovers a purchase whose receipt was lost; a plan change ends the old plan — checked by: `./gradlew :sdk:e2e:test` against the compose stack, locally on Colima and in CI.
- [x] The end-to-end test fails when the SDK is wrong — checked by: negative checks: the plain app user id as account id (the backend must refuse), the replacement left out, the receipt sent before the purchase.
- [x] The public API is closed: no data classes in the contract, `UNKNOWN` instead of `OTHER`, the dump matches — checked by: `./gradlew :sdk:core:checkKotlinAbi` and the list in the ADR; a review of every public symbol.
- [x] `docs/sdk-android.md` and the ADR are complete and match the code — checked by: a review that runs the examples of the guide against the API.
- [ ] `./gradlew build`, the iOS simulator tests, the Konsist tests and the new CI job pass — checked by: the commands and a green pull request run.
- [ ] An independent read-only review of the diff against the criteria above found nothing that blocks — checked by: the review report.

## State model
- **The replacement of a purchase** is part of the request and is explicit: `PlanChange?` (absent for a first purchase); the mode is an enum, not a pair of flags.
- **The cache** is a value with its moment of reception, or nothing. It has no states of its own: every backend answer replaces it, a change of app user drops it. `customerInfo` stays what it was (the last backend answer in this run), separate from `lastKnownCustomerInfo`.
- Nothing else changes.

## Decisions taken
- **`SubscriptionUpdateParams`** for a one-to-one replacement (agent, from the documentation): enough for one product replacing one product. `SubscriptionProductReplacementParams` is for add-ons, which are out of scope.
- **The old purchase is found by the SDK from the owned purchases, the app only names the product to replace** (agent): the app never handles purchase tokens (a secret of the user).
- **An e2e module with Docker** (see the decisions above).
- **No change to the backend** (agent): `linkedPurchaseToken` and the expiry of the old plan already exist and are covered by the conformance suite.
