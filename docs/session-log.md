## 2026-11-06 — Backend part 2d (request limits, refunds before the receipt)
- Goal: stop a client with the public API key from using up the Google quota, and stop a refund that arrives before the first receipt from being lost (ADR 0016). User decisions: a new `rate_limited` error code (a change of the public API of `contracts/`) and limits by client address plus app user id, not by API key.
- What the agent proposed / what I chose: `ktor-server-rate-limit` (it forgets a key when its bucket refills, so memory cannot grow); the limit is counted before authentication so wrong keys are limited too; the forwarded address is read only when the operator says there is a proxy, and then only its last value. Refunds wait in a table and are applied when the receipt arrives; the first version covered only one order of arrival, see below.
- What I had to correct: (1) the first draft of a rate-limit assertion checked that `Retry-After` was exactly 60, which is fragile; it now checks 1 to 60. (2) Four existing expectations changed because behaviour changed on purpose: the contract test that listed the wire names of `ErrorCode`, the contract test that used `"rate_limited"` as its example of an unknown code (it now uses `a_code_from_the_future`, keeping its intent), and a webhook test that expected an unknown refund to be dropped. (3) Two lint findings (a long builder signature and a shadowed lambda name) fixed in the tests.
- Pitest scored the changed classes 69 % (the CI job would have failed): the real logic was killed at 89 %, but 103 of the 182 mutants were Kotlin coroutine plumbing, which only dies when a dependency fails *after* suspending. Instead of touching the configuration or the threshold I wrote a fault-injection test: for eight scenarios (notifications and receipts, subscriptions and one-time purchases, refunds before the receipt, upgrades) each dependency call is made to fail in turn, before and after its work, and the test requires that the failure reaches the caller and that a retry leaves exactly what an attempt without failures leaves. It found one real leftover (a refund waiting for a receipt stayed in the table if clearing it failed right after the purchase was stored), now fixed. Pitest: 81 % on the changed classes, 86 % on all of `domain`.
- A read-only review found, in my own words, that "both orders are covered" was false: the receipt looked for a waiting refund only before asking Google and storing the purchase, so a refund that arrived during the acknowledgement round trip stayed in the table while the user kept access. The receipt now looks again after storing, with a test that puts the refund in the middle of the acknowledgement. It also found that the forwarded address was read from the first header line only (a proxy that adds its own line would let a client choose its key), that an IPv6 host had billions of addresses to rotate, that the key of an invalid user id was the raw path, that retention was applied only when deleting, and that the pending-refund store defaulted to "remember nothing" (now a required parameter, so a wiring omission cannot silently lose refunds again). My first validation of the forwarded address accepted `1.2.3.4:5678` as a key; it now has to parse as an IP.

## 2026-11-06 — Require the account id on Google receipts

The documentation says the field is limited to 64 characters, that personal data in it can block purchases and that a one-way hash is recommended; the id is also the user's secret. One function in `contracts/` is the single definition for SDK and backend; no setting turns the rule off.

The "first one to store the token keeps it" tests were rewritten so that Google names the thief's own account, to keep testing that second line of defence.

## 2026-11-12 — SDK for Android, subphase 1a (the basics)
- Goal: an Android app can configure KuotaKit, show the offerings, buy with Google Play and read what the user may access, with the account id attached to every purchase and no access decided by the SDK. Plan: `docs/plans/2026-11-sdk-android-1a.md` (approved by the maintainer; the SDK is built in subphases and Phase 1 closes only with the complete Android SDK).
- What the agent proposed / what I chose: a Kotlin Multiplatform core (Ktor client, one sealed exception class, an adapter interface the platforms implement) and an Android module with Play Billing 9.1.0 behind a small interface so the rest can be tested without a device; a secret API key (`sk_`) is refused in `configure`; the adapter has no way to acknowledge.
- What I had to correct: (1) my first tests expected the `$` of the app user id to be percent-encoded in the path; Ktor leaves it as it is (it is a valid character) and the backend accepts it, so the expectation was wrong, not the code. (2) OkHttp 5, which the Ktor engine brings, needs `compileSdk` 37: the AAR metadata check failed, so both modules compile against 37 (installed locally; to be seen in CI). (3) Several detekt rules (too many `throw`s, a generic `catch`) led to splitting the API client and the validation in smaller pieces.

Negative checks that failed as they should and were reverted: plain app user id as account id, a refused purchase read as a conflict, the backend called when the user cancels, the customer info cleared on failure, the Android adapter sending an empty account id. Not validated: a real device, the real Google, the CI run (the Android SDK platform 37 may need to download).
- A read-only review found, besides no way for the SDK to report access on its own: the purchase screen could be launched off the main thread, a failed product query was reported as "unknown product", any purchase state but pending was treated as purchased, the app user id could reach a network error message through the cause, an older answer could overwrite a newer customer info, and the "128 random bits" of the id are 122 (a UUID). ## 2026-11-12 — SDK for Android, subphase 1b-i (restore and recovery of purchases)
- Goal: no purchase the user made in the app is lost: the SDK finds them in Google Play and sends them to the backend (`restore()`, a background sync, `ITEM_ALREADY_OWNED` as a recovery). Plan: `docs/plans/2026-11-sdk-android-1b-i.md`, written after reading the official documentation.
- What the agent proposed / what I chose: the documentation changed the plan: Google asks for two mechanisms (the live listener and querying purchases when connecting), says `ITEM_ALREADY_OWNED` is to be handled by fetching purchases, and says purchases made outside the app carry no account id; so the SDK sends only completed purchases with this app user's account id, Google Play is the queue (nothing is stored), there are no timers (the app calls `restore()` when it comes to the foreground), and `minSdk` stays 23 (measured: 9.1.0 and 8.3.0 both need 23, 7.1.1 needs 21 but is past its deadline).
- What I had to correct: (1) my first background tests passed nothing because the mock backend answers on another thread and the test clock is virtual: they now wait for real time. (2) A test showed that updates that arrive during the first sync were lost (listening started after it): both start together now. (3) Android lint, which ran for the first time on this code, found `ConcurrentHashMap.newKeySet` needs API 24 while the SDK supports 23. (4) The adapter was split into a tested `PlayBilling` and a thin real client; this changed the internal interface the old `PlayBillingTest` used, so that file was rewritten with the same tests adapted (and new ones), and one line was added to `FakeBilling` in `KuotaKitTest` for the two new members of `BillingAdapter`; no assertion was weakened.
- Validation done: `./gradlew build` (lint included), the iOS simulator tests, the ABI dump and check. Negative checks that failed as they should and were reverted: purchases of another account sent, a pending purchase sent, the restore stopping at the first refusal, two syncs at once, a failed query read as "nothing owned", updates forwarded while a purchase call waits. Not validated: a real device, the real Google, the CI run.
- A read-only review found 15 things and none that let the SDK report access alone; the ones that mattered were fixed with tests (a purchase waiting for its answer took an update of another product, repeated syncs spent the 10 receipts a minute of the backend, `AlreadyOwned` could be returned for the wrong product, an unexpected exception in the background could end the app, `configure` twice left two syncs). - The CI of `main` after the merge of 1a failed on a flaky test of the iOS job (`anOlderAnswerNeverOverwritesANewerOne`): the test itself raced on which request reached the mock engine first. Fixed in this task (the second request starts after the first has reached the engine) with its negative check; no assertion changed. Lesson: tests with a mock engine and two concurrent requests must not depend on arrival order.

## 2026-11-11 — The CI of the last SDK pull request: a flaky conformance check, and runs GitHub left stuck
- Goal: find out why the job `conformance` failed on the pull request of 1b-ii, fix it, and get the pull request merged.
- What happened: the log showed the whole suite passing (54 of 54) and then the `self-check` failing in its own baseline run, at L2-15, with `429` where `402` was expected. Only the request limiter answers `429`. The runner makes one `Backend` per scenario and each picked a random prefix of 65 536 for its client addresses, starting at the same first address; a scenario that floods an address (the limit scenarios) left it with no budget, so a later scenario with the same prefix got the `429`. The odds per run are low (about one in a hundred, my estimate), which fits a failure that did not reproduce locally in two runs. I could not prove from the log that this collision was the exact trigger; I proved the flaw with a test (3,000 scenarios: the first addresses collided before the fix and do not after) and fixed it with one counter shared by the process and a random start. If a `429` appears again in the suite, this explanation was not the whole story.
- What went wrong afterwards: after the fix was pushed the new CI runs of that pull request stayed `queued` with no jobs, for more than an hour. The same happened to a new pull request on the same branch; one on a freshly named branch started at once. Cancel (`409`/"completed"), force-cancel (`409`, "has not been queued yet") and delete (`403`) all failed on the four runs: GitHub's support assistant, quoting its documentation on troubleshooting workflows, said that this stuck state needs GitHub Support to clear it (self-service cancellation and deletion may not work), and the maintainer opened a ticket. Nothing in the repository, the settings or the billing was wrong (Actions enabled, $0 billed, no incident on the status page); re-enabling Actions did not help. What worked: a new branch from `main` with the same content as one commit (the pull request #21). The two closed pull requests (#19, #20) keep four runs that nobody can remove.
- A lesson: when the CI does not start after a push, check with `gh run list` and the jobs API before blaming the code or waiting; a run with `total_count: 0` jobs that cannot be cancelled is not something to retry in the same branch. Nothing was changed to make a check pass: the test of the fix was written first and failed.
- Validation done: the compose run of the suite and `self-check` on the same containers (what CI does), before and after the fix, `./gradlew :conformance:test` with ktlint and detekt; and the CI of the pull request #21 and of `main` after the merge, all green. Not validated: that the collision was the trigger (see above).
