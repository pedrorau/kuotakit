## 2026-11-03 — Phase 1, task 2: agent guardrails
- Goal: guardrail scripts in `scripts/agent/` (paths, commands, protected tests, format after edit, no "done" in red) that any harness can call, their pytest tests in CI, Claude Code hooks, and the OpenCode and Pi wiring documented.
- What the agent proposed / what I chose: one neutral stdin/exit-code contract plus automatic detection of the Claude Code payload, so the hooks need no flags. Secret patterns are read from `.gitignore` (single source of truth). "Ask a human" is exit 3, and for Claude Code the `permissionDecision: "ask"` JSON. I chose a Stop counter (3 blocks, then a loud warning) over blocking forever, and `check_changed` after every edit.
- What I had to correct: (1) the test `cd backend && rm src/test/...` showed the guards resolved relative paths from the session directory and ignored `cd`, which was a real bypass; fixed in the guard (every `cd` seen so far is now a possible base), not in the test. (2) The reviewer subagent found 3 blockers by running the guards on adversarial commands: combined shell flags (`bash -lc`), wrapper options that take a value (`sudo -u root git push -f`, `timeout 5 ...`, `xargs`), and a Stop hook that Claude Code ignores when it exits 2 with "No such file or directory" (it fails open exactly when Gradle is missing; a block must be the `decision: "block"` JSON). All fixed with tests, plus case-insensitive secrets, `find -delete`, `git clean`/`checkout .`, a shared time budget below the hook timeout, and a fallback when the session wanders outside the repo. Two tests changed their expectations because the contract changed (Stop is now a JSON block; a repo without the secrets block now falls back to the project's own rules), and the assertions still check the block and its reason. (3) A live run showed that Claude Code 2.1.105 (the installed version) never runs hooks in exec form (`command` + `args`) and says nothing, so the first version of `.claude/settings.json` guarded nothing; switched to shell form (works on old and new versions) and added `test_settings.py` so it cannot regress silently. The pytest suite was green the whole time: only the live run could catch it. (4) Hook formats were verified against the official docs, not assumed: `MultiEdit` is no longer documented, the `NotebookEdit` path field is unconfirmed (both `file_path` and `notebook_path` are accepted), and OpenCode cannot enforce a stop guard.
- Validation done: 242 pytest cases pass; each guard was shown blocking its action with the exact Claude Code payloads (`.env`, `git push --force`, `git reset --hard`, `rm -rf` outside build, `npm publish`, `./gradlew publish`, editing an existing test) and the Stop hook blocking 3 times then warning. Live test: headless Claude Code sessions (`claude -p`) in a temp repo with the final `.claude/settings.json`: writing `.env` was blocked, editing an existing test was refused (ask), a new test file was created, ktlintFormat ran after the edit, and a Stop with failing checks was blocked 3 times ("attempt 3 of 3") and then let through.
- Public API: none.

Also fixed: SchemaBuilder silently turned value classes into objects and merged `Box<A>`/`Box<B>`, did not reject duplicate names, returned a live view from `components()`; the webhook 401 text; the Konsist rule now also catches fully qualified platform types.
- Validation done: `./gradlew build` green; `pytest scripts`; negative tests that failed as they should and were reverted: a renamed model field (`checkKotlinAbi` and `checkOpenApi`), a hand-edited `openapi.json`, a `java.*` import in `contracts` (Konsist). ## 2026-11-05 — Backend part 2b (Google Play notifications webhook)
- Goal: `POST /v1/webhooks/google` so renewals, cancellations and above all refunds reach the backend without the app (ADR 0014). One-time products, `linkedPurchaseToken` and rate limiting were split into part 2c (my call, agreed in planning).
- What the agent proposed / what I chose: a notification may only take access away without asking Google (refund, revocation); everything else re-reads `subscriptionsv2` through the same mapper as the receipts. Dedupe by Pub/Sub `messageId`, recorded after handling. The payload is read as a JSON tree so no `@Serializable` appears outside `contracts/`. Google's own `GoogleIdTokenVerifier` for the OIDC token.
- What I had to correct: (1) my first verifier treated every `IOException` as "Google's keys are unreachable"; a test with a garbage token while the keys are down showed that a forged push would be retried by Pub/Sub for days, and that a malformed token threw `IllegalArgumentException` (a 500). The token is now parsed first (invalid = 401) and only the key fetch can mean 502. (2) Two private test classes with the same name in one package (`Setup`, `Backend`) did not compile; renamed. (3) I had planned to use the plan-mode tool, but the plan file could not be written (`EACCES`) while the tool still reported "approved"; I did not treat that as approval and showed the plan in the chat instead.
- A read-only review pass found two HIGH problems in my first version, both real: (1) "final" was enforced only inside the notification service, so the receipt endpoint could bring a refunded purchase back, and (2) a slow renewal read could overwrite a refund that landed meanwhile and the refund would never be retried. Both are fixed in `PurchaseRepository.save` (the check is in the SQL statement) with a contract test run on the in-memory fake and on real Postgres; removing the guard makes it fail (checked). It also found that malformed authenticated pushes answered 400 (Pub/Sub would retry them for days): they are now acknowledged and logged, which removed the 400 from the contract; and that my "64 KiB" limit was really 16 KiB, so the code, ADR and test now agree. Two limits are documented instead of fixed: a refund that arrives before the first receipt, and last-write-wins between non-final updates.
- Test fakes now `yield()` like real I/O: Pitest scored the new classes 63 % because the kotlin coroutine resume paths never ran; with suspending fakes they are covered (75 % on the new classes, 85 % on the 2a ones, 81 % on all of `domain`).
- Validation done: `./gradlew build` green with 213 backend tests (real Postgres through Colima); `pytest scripts` 304; license headers; Pitest on the changed classes and on all of `domain`; negative tests that failed as they should and were reverted: removing V3, removing the final-status guard. Not validated: the real Pub/Sub and the real Play.

## 2026-11-06 — Backend part 2d (request limits, refunds before the receipt)
- Goal: stop a client with the public API key from using up the Google quota, and stop a refund that arrives before the first receipt from being lost (ADR 0016). User decisions: a new `rate_limited` error code (a change of the public API of `contracts/`) and limits by client address plus app user id, not by API key.
- What the agent proposed / what I chose: `ktor-server-rate-limit` (it forgets a key when its bucket refills, so memory cannot grow); the limit is counted before authentication so wrong keys are limited too; the forwarded address is read only when the operator says there is a proxy, and then only its last value. Refunds wait in a table and are applied when the receipt arrives; the first version covered only one order of arrival, see below.
- What I had to correct: (1) the first draft of a rate-limit assertion checked that `Retry-After` was exactly 60, which is fragile; it now checks 1 to 60. (2) Four existing expectations changed because behaviour changed on purpose: the contract test that listed the wire names of `ErrorCode`, the contract test that used `"rate_limited"` as its example of an unknown code (it now uses `a_code_from_the_future`, keeping its intent), and a webhook test that expected an unknown refund to be dropped. (3) Two lint findings (a long builder signature and a shadowed lambda name) fixed in the tests.
- Pitest scored the changed classes 69 % (the CI job would have failed): the real logic was killed at 89 %, but 103 of the 182 mutants were Kotlin coroutine plumbing, which only dies when a dependency fails *after* suspending. Instead of touching the configuration or the threshold I wrote a fault-injection test: for eight scenarios (notifications and receipts, subscriptions and one-time purchases, refunds before the receipt, upgrades) each dependency call is made to fail in turn, before and after its work, and the test requires that the failure reaches the caller and that a retry leaves exactly what an attempt without failures leaves. It found one real leftover (a refund waiting for a receipt stayed in the table if clearing it failed right after the purchase was stored), now fixed. Pitest: 81 % on the changed classes, 86 % on all of `domain`.
- A read-only review found, in my own words, that "both orders are covered" was false: the receipt looked for a waiting refund only before asking Google and storing the purchase, so a refund that arrived during the acknowledgement round trip stayed in the table while the user kept access. The receipt now looks again after storing, with a test that puts the refund in the middle of the acknowledgement. It also found that the forwarded address was read from the first header line only (a proxy that adds its own line would let a client choose its key), that an IPv6 host had billions of addresses to rotate, that the key of an invalid user id was the raw path, that retention was applied only when deleting, and that the pending-refund store defaulted to "remember nothing" (now a required parameter, so a wiring omission cannot silently lose refunds again). My first validation of the forwarded address accepted `1.2.3.4:5678` as a key; it now has to parse as an IP.
- The maintainer asked me to check the proxy concern on his machine. Measured with Colima: a container sees every client of a published port as the Docker gateway (`localhost` and the LAN address alike), and with the real stack and a limit of 3 a minute two routes shared one budget. As a consequence: wrong keys now have a bucket of their own, so they cannot use up the budget of good keys, and the backend logs one warning when it sees `X-Forwarded-For` with the setting off. His ideas (behaviour patterns, replacing a leaked id, Redis) are in `docs/roadmap.md`, not built.
- Validation done: see the PR. Negative checks that failed as they should and were reverted: putting good and wrong keys in one bucket, removing the general limit, removing the per-user limit, always trusting the forwarded header, ignoring the pending refund in the receipt, not looking again after writing the refund down, removing migration V4. Not validated: real traffic, several instances, the real Google.
- Public API: `ErrorCode.RATE_LIMITED` added to `contracts/`.
- Time spent: n/a · Diff accepted as-is: pending
